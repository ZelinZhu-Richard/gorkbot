# UI Reference Intake

Add screenshots or recordings only when you can explain what product behavior they demonstrate.

For each reference, create a Markdown note:

```yaml
reference_id:
product:
surface:
date_captured:
source:
permission_or_public_status:
```

Then answer:

- What user problem does this interaction solve?
- What information is visible?
- What decision can the user make?
- What state is hidden?
- What is good?
- What fails?
- What principle should we adopt?
- What exact branding or layout must not be copied?

## Initial interface principles

- The current task owner must always be visible.
- Working, waiting, blocked, approval-needed, completed, failed, and unverified states must be distinct.
- Users should see concise activity, not private chain-of-thought.
- Every consequential action should show target, scope, inputs, expected effect, reversibility, and approval status.
- Results should be first-class artifacts, not buried in chat.
- Handoffs should show sender, receiver, requested result, ownership, and return state.
- A user must be able to stop or redirect work without searching through settings.
- Evidence should be one click from a completion claim.
- Notification design should distinguish urgent intervention from ordinary completion.

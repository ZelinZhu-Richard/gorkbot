## Screening implications

1. **STRONG INFERENCE:** GitHub issue-to-PR work is strategically attractive but crowded. Two current first-party sources already cover the core issue, cloud execution, pull-request, testing, and review sequence (SRC-064, SRC-065). A new product cannot treat that sequence alone as differentiation.
2. **STRONG INFERENCE:** citations alone are not a differentiated competitive-intelligence promise. A general deep-research product returns cited reports, while purpose-built CI products monitor product, pricing, website, and news changes (SRC-066 through SRC-068).
3. **STRONG INFERENCE:** generic wrappers face purpose-built competition in analytics, customer-research synthesis, and literature intelligence, including governance or evidence-linking features (SRC-069 through SRC-071).
4. **STRONG INFERENCE:** website-release preparation has a strong existing branch/preview/merge workflow, and current coding agents already cover code changes (SRC-065, SRC-072).
5. **STRONG INFERENCE:** browser-only operations may expose a meaningful reliability problem, but the same documented failure modes make it a higher-risk first prototype (SRC-073, SRC-074). This is a technical-risk inference, not customer-pain evidence.
6. **DESIGN PROPOSAL:** if source-backed competitive intelligence is tested first, narrow it to a verification-first change ledger: explicit source allowlist, prior snapshot, before/after evidence, retrieved-at time, materiality rule, unknown-state handling, approval before updating the master record, and readback after the update. Whether buyers value that contract remains an open question.
